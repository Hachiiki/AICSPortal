AICS Information project thing.

The problem I'm having — and I know I'm not the only one — is that the school has "Computer Studies" right in its name. Asian Institute of Computer Studies. Yet everything still runs on paper. We're stuck in the late 90s. The point of this project is to actually use the tech we have. Put it to work.

I want a portal. Something I can log into and see my grades, my schedule, my info — in real time. No more waiting for a printed report. That transparency matters. Students should see where they stand.

Same goes for teachers. If students can access their grades, teachers should be able to manage them online. Submit, lock, done. No more spreadsheet shuffling.

Admins too. Branch-scoped. Each admin only sees their own campus. Students, teachers, rooms, schedules, documents — all of it.

Stack: Next.js 16 (App Router), React 19, TypeScript 5, Bun, Tailwind CSS 4, shadcn/ui, Lucide React, Framer Motion, Sonner, MongoDB, Cloudinary.

Branch detection baked in. You log in, the app reads your branchId, redirects to /portal/[branch]/[role]. Custom features per campus later.

Three roles:

- Students
- Teachers/Faculty
- Administrators

Algorithms used:

Password auth: bcrypt (cost 12) for hashing. Constant-time comparison. JWT in httpOnly cookie, 7-day expiry, rotated on refresh.

Face recognition: face-api.js TinyFaceDetector + FaceLandmark68Net + FaceRecognitionNet. 128-dim embeddings. Euclidean distance with 0.6 threshold. Enrollment stores embedding only — never the image. Login compares live embedding against stored. Falls back to password on failure. No liveness detection — documented honestly as convenience, not security. (later be implemented once everything is settled)

Grade computation: weighted average — prelim 30%, midterm 30%, finals 40%. Missing periods redistribute weight. Rounded to 2 decimals. Remarks: ≥90 Excellent, ≥85 Very Good, ≥80 Good, ≥75 Passed, ≥70 Conditional, else Failed.

Schedule grid: 6×9 matrix (Mon–Sat × 8–16). Each section's schedule paints cells. Overlap detection flags conflicts. Teacher/room conflict check runs on every schedule create/edit — O(n) scan of existing assignments for same timeslot.

Enrollment prerequisite check: topological sort on curriculum graph. Student's completed subjects (final ≥75) vs required prerequisites. Blocks enrollment if any missing.

Capacity check: atomic counter on subject document. Decrement on enroll, increment on drop. Prevents race conditions.

Conflict detection (schedules): sweep-line algorithm. Sort all assignments by start time. Track active teachers/rooms. Overlap = conflict.

Search: MongoDB text indexes on name, email, studentId, subjectCode. Compound indexes on (branchId, role, status) for role-scoped lists.

Audit logging: append-only. Every sensitive action writes one document with actor, target, before/after values, timestamp, IP, user agent. Immutable.

Notifications: write to notifications collection. If user has active WebSocket, push real-time. Else pull on next page load.

COE PDF: client-side jsPDF + autotable. Fetches current-term enrollments, builds table (code, name, units), totals units, adds registrar signature line and issue date.

Information flow outline:

1. Login
   - Credentials → /api/auth/login → bcrypt verify → JWT cookie → middleware attaches user + branchId
   - Face → webcam → face-api.js embed → compare against branch users → match → same JWT flow
   - Middleware protects all /portal/* routes, redirects unauthenticated to /login

2. Branch scoping
   - Every API handler reads request.user.branchId
   - Query helper auto-injects { branchId: user.branchId } into every find/update/delete
   - No cross-branch leaks possible at query level

3. Student dashboard load
   - Parallel fetches: /api/student (profile), /api/grades (current term), /api/schedule (grid), /api/tasks (today)
   - Grades: enrollments → subjects → grade records → compute weighted final → remarks
   - Schedule: sections → schedules → paint 6×9 grid → conflict flags
   - Tasks: enrollment subjects → activities → status (graded/pending/missing/needs attention)

4. Teacher grades
   - Teacher opens section → fetches roster (enrollments + student info)
   - Enters grades per period → bulk upsert to grades collection
   - On submit: lock flag set, audit log written, notifications created for each student
   - Admin unlock: writes unlock reason, clears lock, audit log, notifies teacher

5. Enrollment period
   - Admin sets enrollment_periods dates
   - Student clicks enroll → checks period open → prerequisites (topo sort) → capacity (atomic counter) → conflict (sweep-line) → creates enrollment doc
   - Admin bulk enroll: same checks, batch insert

6. Schedule management
   - Admin creates schedule → conflict check (teacher + room) → if clean, write schedule doc
   - Teacher requests change → creates request doc → admin reviews → if approved, marks original temporary, writes new schedule, audit log

7. Documents
   - Student uploads → Cloudinary → document record with pending status
   - Admin verifies/rejects → status update → notification to student
   - COE generation: client fetches enrollments → jsPDF builds blob → download/print

8. Notifications
   - Any state change (grade posted, doc verified, request decided, announcement) → create notification doc
   - WebSocket server pushes to connected clients
   - Fallback: poll /api/notifications on page focus

9. Audit trail
   - Middleware wraps sensitive routes (grades, enrollments, users, schedules, documents)
   - On mutation: capture before state, perform write, capture after state, write audit_log
   - Immutable — no update/delete on audit_logs collection

10. Reports
    - Admin requests report → aggregation pipelines (student count by course, grade distribution, attendance rates, etc.)
    - Results formatted → PDF/Excel/CSV export via serverless function

11. Search
    - Global search bar → text index query across users/subjects/rooms/sections/documents
    - Results grouped by type, scoped to branchId
